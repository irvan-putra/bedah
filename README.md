# bedah - self-review canvas

A full-screen review canvas that reviews its own repository. The cards,
diagrams and code facts on the page describe this repo's source at the
pinned commit, so the page is both the review surface and the thing under
review. Extracted from the intodo (now tindak) review canvas, which keeps its own
unchanged page at <https://vanipy.com/tindak/review/>.

Live at <https://vanipy.com/bedah/>.

## What it is

- A static React + esbuild page. No backend, no platform dependency
  (`files-shim.tsx` replaces the hosted-page component kit with a tiny
  localStorage-backed `useLocalState`).
- Full-screen, FreeForm/Miro-style infinite canvas: drag to pan, pinch to
  zoom, one continuous map from the C4 system-context level down to
  containers, sections, components and code - no layer jumps. Cards are
  fixed in place; review marks and camera position stay in the visitor's
  browser only (localStorage), nothing is sent anywhere.
- Relationship lines labeled as references come from a static name/import
  scan at the pinned commit, not proven runtime calls. One-time history
  (the intodo extraction) is documented in the page's Menu under
  "About / history", not drawn on the map.

## Content and honesty

The cards describe this repository and are generated from it:

- `src/sections.ts` - the review sections (file inventory, line counts,
  per-section digests).
- `src/code.ts` - the C4 component layers (components, curated
  responsibilities, declarations, static references).

Both carry the commit they were generated from, shown in the UI, so the
cards never claim to describe a newer bedah than they do. The generated
files are excluded from their own digests - a self-referential content hash
can never stabilise. To refresh the content after the source changes:

    python3 tools/gen_sections.py --repo /path/to/bedah --out src/sections.ts
    python3 tools/gen_code.py    --repo /path/to/bedah --out src/code.ts

Both generators take any local bedah checkout (`--commit` / `--from-git`
for exact pinning) and change nothing else in this repo.

## The map

The canvas is one fixed territory: zoom only shows or hides detail. Containers
hold components, components hold file rooms, file rooms hold declaration
chips. Review cards (marks, findings) live in the Menu. The Menu also holds
the component list and the trail toggles (ship flow, content refresh), which
only emphasise routes already drawn faintly on the map.

`src/codemap.ts` (generated by `tools/gen_code.py`) is the code map:

- TypeScript/TSX: the TypeScript compiler API with its type checker
  (`tools/ast_ts.mjs`, run through `node`, `typescript` is a devDependency).
- Python: the standard library `ast`.
- Workflow YAML (jobs, steps, `paths:`, `run:`), Markdown (headings) and
  `package.json` (dependencies): line or JSON scans.
- File-level only: shell, CSS, HTML, lockfiles, `.gitignore`, `.mjs`, and the
  generated `src/code.ts` / `src/codemap.ts`.
- Inventory: every file from `git ls-files -co --exclude-standard` (minus
  `node_modules`) is listed. A file no component in `CONFIG` owns is shown as
  unassigned in the Menu, never dropped. Binary or media files are listed as
  inventory-only with their size; their contents are not analysed. Untracked
  files are included so a pre-commit run sees new work; run the generator on a
  clean checkout for the published map.
- Comments and docs, structural only: a comment block, JSDoc or Python
  docstring directly above a declaration is attached to it as the author's
  words with file and line, labelled unverified. It never creates a relation.
  A backticked token in a Markdown file that exactly equals a tracked path, a
  file name or a unique declaration name is listed as a text mention
  (`CM_DOCREFS`, with file and line). Nothing interprets prose, and a mention
  is not evidence that the prose is true or current.

Edge kinds, none of them a proven runtime call: `imports`, `calls-resolved`,
`renders-resolved`, `refs-resolved`, `type-ref-resolved` (static resolution by
the compiler or Python scope rules), `generated-by` (a generated file's own
header), `run-step`, `path-trigger`, `path-mention` (text evidence). Calls
through callbacks, dynamic imports or untyped values are not seen. The
component grouping and the one-line responsibilities are written directly in source.
`python3 tools/gen_code.py --map-mode regex` runs the earlier line scan, kept
only for comparison: `tools/compare_extractors.py` classifies the differences
against the source (the regex scan gave `snapEnds` a span of about 450 lines
instead of 20 and produced 104 false edges that way; it also missed constants
declared on a shared line).

Before/after comparison (frozen fixture, same 21 files read by both runs,
manifest sha256 of the file list `799e0537...1a58`, base `4f99634` plus local
changes; the fixture itself is not published): regex 216 declarations and 405
typed edges, AST 231 and 343. The name-based edges are 373 (regex: 335
same-file-name + 38 imported-name) and 311 (AST: resolved kinds); the other 32
in each are the structural kinds (imports, generated-by, run-step,
path-trigger, path-mention). Name-edge pairs: 262 in both, 111 regex-only (104
caused by span overshoot, 6 containment through inner functions, 1 words in
JSX prose), 49 AST-only (30 parent/inner, 14 involving declarations the regex
never found, 5 spread syntax). Regex mislabelled 3 constants as functions and
missed 11 constants on shared lines; 4 Python nested defs only exist since the
AST pass was written. The final map counts in `src/codemap.ts` come from a
different corpus (the final worktree) and are not comparable to these.

## Build and deploy

    sh build.sh          # writes dist/: index.html + fingerprinted assets

Every push to `main` deploys automatically through
`.github/workflows/deploy.yml`: an unprivileged build job (`contents: read`
only, locked `npm ci --ignore-scripts`, esbuild) produces the artifact, then
the only privileged job (`pages: write`, `id-token: write`, github-pages
environment) deploys it and polls the live URL until it serves the exact
built bytes (`tools/verify_live.sh`). A green check means live, not just
pushed.
