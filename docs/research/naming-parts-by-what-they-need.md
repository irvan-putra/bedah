# Tanya, pasti, muatan: naming a project's parts by what they need

Status: design proposal and taxonomy analysis, not a feature release. Bedah source inspected at `e54a64438df5bc1cb9bcc9602a185c447f9a9804` (2026-11-20). External sources checked 2026-11-20 (WIB). No code changes accompany this note, and the names below are proposals, with alternatives listed.

Revision of 2026-11-20: the first draft named the three central kinds **otak**, **hitung** and **benda**. Read cold, "otak" suggests the human brain rather than model dependence, "hitung" suggests numeric calculation only, and "benda" (a physical thing) leaves no obvious room for documents. The names below were chosen to say their meaning without a disclaimer. The rest of this note uses the revised names throughout; the analysis itself is unchanged.

Illustrated version of this proposal: <https://vanipy.com/bedah/naming/>.

## The idea

A review canvas should show, for each part of a project, **what that part needs in order to run**:

1. an AI model, so the part stops working when the model is gone;
2. plain deterministic code, so the part runs the same way every time without any model;
3. nothing at all, because the part is inert content.

The immediate question this answers for a reader: how much of this project is the model, and how much stands on its own?

## Proposed names

Short Indonesian words, matching this project's naming conventions. Alternatives considered are noted in parentheses.

| Kind | Name | Meaning |
| --- | --- | --- |
| AI at runtime | **tanya** | The part *asks* a model while the app runs; no model, no answer. Includes model weights and prompt templates: their bytes sit still, but their behavior comes from the model. (minta, pinjam) |
| Algorithm | **pasti** | Deterministic code, *certain*: same input, same output, no model. Parsers, schedulers, generators, comparators. (tetap, ajeg) |
| Static content | **muatan** | Inert content the project *carries*: markup, styles, icons, images, data files, and documents shipped as content, including data generated by the project's own tools at build time. (konten, sajian, wujud) |
| Wiring | **kait** | Configuration that binds the parts: package manifests, lockfiles, CI workflows, ignore files. |
| Words | **kata** | Prose for people: README, docs, comments. |
| Tests | **uji** | Tests and fixtures: they prove behavior but ship nothing. |
| Outside services | **jauh** | Services the project calls but does not contain: a hosted model endpoint, a paid API. |
| Unknown | **kabut** | Anything the classifier cannot place: still *in the fog*. A first-class bucket, shown and never dropped. (asing, gaib) |

One tag, not a kind: **bekas** (a trace) marks parts an AI wrote at build time that now run without any model.

Choosing **tanya** for AI-at-runtime frees the first draft's name for the unknown bucket, which moved to **kabut**; if tanya stays with the unknowns instead, **minta** is the cascade-free name for AI at runtime.

## Where documents live

Documents are not homeless in this split. Prose written for people (a README, design notes, research like this note) is **kata**. A document the project ships as content (a PDF guide an app displays) is **muatan**. The first draft's "benda", a physical thing, hid both; "muatan", what a project carries, holds the second without swallowing the first.

## Is the three-way split exhaustive?

No. Checking the three kinds against a real repository (this one) turns up four more kinds every repo has and one it needs:

- **kait**: `package.json`, the lockfile, `.github/workflows/deploy.yml` and `.gitignore` are neither logic nor content, but the project breaks without them.
- **kata**: `README.md` and `docs/research/*` are prose. Bedah already treats comments and docs as structural only and unverified; kata is the same honesty applied at the kind level.
- **uji**: tests and fixtures prove behavior and ship nothing, so they are neither pasti nor muatan.
- **jauh**: a hosted model endpoint or any outside service leaves no file in the repo, so a file scan alone can never find it. The repo has to declare these, or they stay invisible.
- **kabut**: a classifier that silently forces every file into a bucket hides its own uncertainty. Bedah already shows unassigned files rather than dropping them; kabut extends that rule to kinds.

## Is it overlapping?

Yes, and the overlaps are instructive:

- A model weights file is static bytes with AI behavior. Resolution: classify by behavior (tanya), keep the file form as a note.
- A prompt template is plain text that means nothing without the model: tanya, not muatan.
- Code an AI wrote at build time now runs deterministically: pasti, carrying the bekas tag.
- Generated data such as this repo's own `src/sections.ts`, `src/code.ts` and `src/codemap.ts` is muatan produced by pasti, one build step apart.

## Build-time AI is not runtime AI

The split that matters most is not a kind at all. Whether AI **wrote** a part (provenance, build time) and whether a part **calls** AI (dependence, runtime) are independent questions. Mixing them is how every AI-assisted project ends up looking like it is all AI.

- A file written by AI at build time but running with no model is pasti or muatan with a bekas mark.
- A part that asks a model at runtime is tanya, whether a human or an AI typed it.

Provenance cannot always be read from the repo: git history records commits, not authorship. Where authorship is not recorded, bekas is itself unverified and should be labeled that way.

## Fit to the current repo

Applied to Bedah at the inspected commit, by the file groups in the README:

| Files | Kind |
| --- | --- |
| `tools/gen_code.py`, `tools/ast_ts.mjs`, `tools/gen_sections.py`, `tools/compare_extractors.py` | pasti |
| `App.tsx`, `main.tsx`, `files-shim.tsx`, `build.sh` | pasti |
| `src/sections.ts`, `src/code.ts`, `src/codemap.ts` | muatan (generated at build time) |
| `index.html`, styles, `pages/*` | muatan |
| `package.json`, lockfile, `.github/workflows/deploy.yml`, `.gitignore` | kait |
| `README.md`, `docs/research/*` (including this note) | kata |

Two absences are worth drawing, not just presences: Bedah today has **no tanya** (the whole page runs without a model) and **no uji** in the repo (the extractors are checked with a comparison tool and an unpublished fixture, per the README).

**Proposal, not implemented:** draw the kinds as a tint or badge on the existing rooms and declarations without moving the territory; keep the legend and the kabut list in the Menu beside the unassigned files; carry evidence on every mark (a model import or endpoint seen by the extractor, a declaration by hand, or unverified), matching the labels Bedah uses now; and keep the classification itself deterministic, run by the same AST and name scans Bedah already has, rather than asking a model to judge the repo.

## Related public work

- [SPDX 3.0 AI package profile](https://spdx.github.io/spdx-spec/v3.0.1/model/AI/Classes/AIPackage/) records AI packages in a software bill of materials.
- [CycloneDX ML-BOM](https://cyclonedx.org/capabilities/mlbom/) covers model and dataset inventory for security review.
- [C4](https://c4model.com/), already used by Bedah, separates architecture scope, not part kinds.

These record that a model is present in an inventory. None of them tries to draw which parts of one project are model-dependent, which is the gap this idea addresses. This note has not surveyed academic work on software decomposition; other taxonomies may exist there.

## Limits and open questions

- jauh dependencies cannot be discovered by file scanning; they need declarations or conventions this note does not define.
- Whether a part "needs" a model can be conditional (optional features, graceful fallbacks). The kinds may need a condition or confidence note per mark.
- The boundary between pasti and muatan blurs for declarative config that drives behavior (kait was separated partly for this reason).
- Names are proposals; the alternatives in parentheses are open.
